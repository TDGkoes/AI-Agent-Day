# GHCP Harness Hands-on Lab — 60분 강의용 스크립트

교안은 상세 참고 자료로 유지하고, 강의에서는 핵심 표·그림을 짚은 뒤 바로 실습합니다. 인용문은 발화, ‘진행’과 ‘확인’은 화면 조작 안내입니다.

## 강의 전 준비와 운영 기준

- 로그인·생성 권한·실습 파일 다운로드는 교육 전에 완료합니다. 사용할 환경은 Contoso(default)입니다.
- 공통 인력·제안 참고·WBS 참고 자료는 SharePoint에 준비하고 학습자의 접근 권한을 확인합니다.
- 강사용 Project Delivery 에이전트 완성본, 같은 RFP의 분석 결과·중간 계획 데이터·PPTX·XLSX와 실행 기록을 준비합니다.
- **표 전체를 읽지 않습니다.** 한 페이지에서 핵심 하나와 Project Delivery 에이전트의 예 하나만 말합니다. 세부 용어·예외·설계 비교는 질문이 있을 때 설명합니다.
- 실습은 **한 동작 보여주기 → 학습자 따라 하기 → 완료 화면 확인**으로 진행합니다. 입력·업로드 중에는 추가 설명을 이어 가지 않습니다.
- 먼저 끝난 학습자는 자신의 등록·저장 상태를 확인합니다. 남는 시간에는 뒤 단계 실습을 앞당기거나 진행이 늦은 학습자를 지원합니다.
- 생성 대기에는 질문을 받습니다. 질문이 없으면 결과나 실행 기록의 한 항목만 함께 확인합니다.
- 38분에는 테스트, 58분에는 마무리로 전환합니다. 생성이 지연되면 실행 상태를 유지하고 준비한 강사 결과로 시연합니다. 사전 실행 결과임을 밝힙니다.

## 1. 홈 · 00~02분

**띄울 위치:** 홈 → **2. 완성할 에이전트와 업무 흐름**의 두 번째 이미지인 업무 흐름도. 그림 전체가 보이도록 맞추고 자기소개·업무 소개를 진행합니다. 목적을 말할 때는 바로 위의 ‘프로젝트 산출물 작성, 더 쉽고 빠르게’ 이미지를 잠깐 보여줍니다.

**실습 준비 확인:** Copilot Studio 탭으로 전환해 환경 이름을 짚습니다. 자료를 못 받은 학습자가 있을 때만 홈 → **1. 학습 목표와 준비사항 → 시작 전 확인**의 다운로드 링크로 이동합니다.

> 안녕하세요. 앞서 소개드린 에이전트 5종 중 Project Delivery 에이전트를 개발한 (회사명) (팀명)팀 (이름) 매니저입니다. 오늘은 RFP라는 고객의 사업 요구 문서를 읽고, 제안서와 작업 일정표인 WBS를 만드는 Project Delivery 에이전트를 함께 구성하겠습니다. 개발한 Project Delivery 에이전트는 견적서도 다루지만 오늘 실습에서는 제외합니다.
>
> 그림처럼 요구사항을 분석하고, 중간 작업 계획을 세운 뒤, PowerPoint 제안서와 Excel WBS를 만듭니다. Project Delivery 에이전트가 초안을 만들고 사람이 검토·수정해 고객에게 전달하는 것이 목적입니다.
>
> 오늘은 업무 방법과 필요한 도구·자료를 연결하고, 실제로 실행해 결과를 확인해 보겠습니다. Copilot Studio의 Contoso(default) 환경과 내려받은 실습 파일을 준비해 주세요.

**확인:** 환경 이름과 실습 파일 준비 여부. 업무 단계별 세부 항목은 여기서 설명하지 않습니다.

## 2. GHCP Harness 개요 · 02~05분

**띄울 위치:** GHCP Harness 개요 → **1. GHCP Harness의 기본 개요와 특징 → Agentic Loop — 하나의 요청을 해석하고 처리·검증하는 과정**의 그림. 하네스 소개부터 반복 실행 설명까지 이 그림을 띄워 둡니다.

**선택 이유 설명:** **3절의 GHCP Harness 선택 이유** 세 항목이 보이는 위치로 이동합니다. 2절의 비교표는 질문이 있을 때만 보여줍니다.

> 하네스는 AI가 판단한 일을 실제로 실행하도록 돕는 환경입니다. 오늘 사용하는 GHCP 하네스는 업무 방법과 도구를 활용하고 PowerPoint·Excel 파일도 만들 수 있습니다. 화면에 Microsoft Copilot 하네스로 표시될 수도 있습니다.
>
> 그림을 보겠습니다. ‘RFP를 분석해줘’라고 하면 요청을 이해하고, 어떻게 처리할지 계획한 뒤, 필요한 기능을 골라 실행합니다. 결과가 부족하면 확인하고 보완합니다. 이 과정을 Agentic Loop라고 합니다. 분석만 요청했다면 분석까지 수행합니다.
>
> Project Delivery 에이전트는 분석부터 문서 작성까지 여러 작업을 연결해야 했고, 직접 구축했을 때 파일 작성 품질도 만족스러워 GHCP를 선택했습니다.
>
> 그럼 직접 만들어 보겠습니다. 실습에는 가상 RFP와 인력·참고 문서를 사용하며, 지식 자료는 SharePoint에 준비되어 있습니다.

**진행:** 남는 시간은 환경·파일 준비 지원에 사용합니다. 다섯 특징이나 Standard 비교표를 항목별로 읽지 않습니다.

## 3. 에이전트 생성 및 지침 작성 · 05~12분

### 05~06분 — 지침 구조표로 한 가지 설명

**띄울 위치:** Step1. 에이전트 생성 및 Instructions 작성 → **3. 에이전트 이름 및 지침 입력 → 지침은 어떻게 구성할까?**의 ‘기본 구조 / 작성할 핵심 / 이렇게 구성한 이유’ 표. 표 전체가 보이게 맞춥니다.

> 지침은 에이전트가 전체 업무에서 지킬 기준입니다. 이 표처럼 ‘무슨 일을 맡길지’, ‘어떤 순서로 할지’, ‘무엇을 지킬지’를 정합니다. Project Delivery 에이전트의 지침에는 RFP 분석과 문서 작성을 맡기고, 확인되지 않은 사실을 만들지 않도록 했습니다. 표는 이런 기준을 정리한 것이고, 지침을 반드시 표로 쓸 필요는 없습니다.

**다음 화면:** 바로 아래 **준비된 지침 입력·저장**에서 ‘에이전트 지침’을 펼칩니다. ‘역할과 범위’와 ‘공통 원칙’ 위치만 짚고, 내용 전체를 계속 스크롤하며 설명하지 않습니다.

### 06~12분 — 생성·이름·지침 입력 실습

**실습 화면:** Copilot Studio 홈 → 에이전트 카드 → 편집 화면의 이름·안내 영역. 학습자가 위치를 놓치면 교안 **2. GitHub Copilot 표시가 있는 에이전트 카드 선택**과 **3. 에이전트 이름 및 지침 입력**의 캡처로 돌아가 해당 위치를 짚습니다.

> 에이전트 카드를 선택해 Project Delivery 에이전트를 만들겠습니다. 이름은 ProjectDelivery_HandsOn_본인이니셜 형식으로, 본인 이니셜을 넣어 입력하고, 준비된 지침을 안내 영역에 붙여 넣은 뒤 저장해 주세요.

**함께 조작**

1. 교안 이미지의 GHCP 에이전트 카드 선택.
2. 에이전트 이름에 `ProjectDelivery_HandsOn_본인이니셜` 입력. `본인이니셜`은 본인의 이니셜로 변경.
3. 안내 영역의 기본 내용을 제공된 지침으로 교체.
4. 저장.

**완료 확인 발화**

> 이름과 지침이 저장됐는지 확인해 주세요. 이제 개별 업무 방법을 등록하겠습니다.

**진행:** 따라 하기와 저장 확인에 시간을 씁니다. 지침 전문을 낭독하지 않습니다.

## 4. 스킬 등록 · 12~24분

### 12~14분 — 세 Skill의 책임 표로 설명

**띄울 위치:** Step2. Skills 구성 → **3절의 업무 분리 기준과 Skill 구성**을 정리한 ‘Skill / 맡은 작업 / 분리한 이유’ 표. 지침과 Skill의 차이, 세 업무의 역할을 이 표에서 설명합니다.

**추가로 짚을 위치:** 결과를 이어 쓰는 문장에서는 **5절의 여러 Skill 결과 연결 사례**를 보여주는 흐름도를 보여줍니다. 템플릿 복사 설명은 같은 화면에서 짧게 말하고, 부록의 비교 그림은 질문이 있을 때만 엽니다.

> 지침이 전체 규칙이라면, Skill은 특정 업무의 작업 방법입니다. 표처럼 분석은 요구사항을 정리하고, WBS는 작업과 일정을 만들고, 제안서는 고객에게 설명할 문서를 만듭니다. 맡은 일이 달라 세 개로 나눴습니다.
>
> Skill에는 ‘무엇을 받아서, 어떻게 처리하고, 무엇을 내놓을지’를 적습니다. Project Delivery 에이전트는 앞에서 정리한 청사진과 인력을 다음 작업에서도 이어 쓰도록 했습니다. 같은 WBS Skill이 중간 계획을 만들 때와 최종 Excel을 만들 때 사용됩니다.
>
> 제안서와 WBS에는 표준 템플릿도 함께 넣었습니다. 양식을 흉내 내 새로 그리기보다 원본 파일을 복사해 내용을 바꾸도록 했습니다. 슬라이드 수와 내용은 제안에 맞게 바꿀 수 있습니다.

**진행:** Skill 전문과 템플릿 방식 비교는 펼쳐 읽지 않습니다. 입력·출력 위치는 업로드할 문서에서 한 번만 짚습니다.

### 14~24분 — 세 Skill 등록 실습

**실습 화면:** Copilot Studio의 Skill 업로드 화면. 분석 등록은 교안 **6. Skill 등록 → 6.1 분석 Skill 등록 — .md 파일**, 제안서·WBS 등록은 **6.2 제안서/WBS Skill 등록 — 템플릿을 포함한 .zip 파일**의 캡처를 따라갑니다. 완료 후에는 Project Delivery 에이전트의 Skill 목록을 띄웁니다.

> 분석은 압축을 풀어 SKILL.md를 등록합니다. 제안서와 WBS는 템플릿이 함께 필요하므로 ZIP 그대로 등록해 주세요. 제가 하나씩 보여드리면 같은 순서로 따라 해 주세요.

| 순서 | 학습자 조작 | 함께 확인 |
|---|---|---|
| 1 | 분석 패키지를 풀어 SKILL.md 업로드 | 분석 Skill이 목록에 표시됨 |
| 2 | 제안서 패키지를 ZIP 그대로 업로드 | 제안서 생성 Skill이 표시됨 |
| 3 | WBS 패키지를 ZIP 그대로 업로드 | WBS 생성 Skill이 표시됨 |

**완료 확인 발화**

> 목록에 세 Skill이 보이는지 확인해 주세요. ZIP은 등록 파일이고, 실제 업무 결과는 PowerPoint와 Excel입니다.

**진행:** 오류가 있으면 선택한 파일과 업로드 상태부터 확인합니다. 먼저 완료한 학습자는 Skill 이름·설명과 지침의 작업 연결을 대조합니다. 긴 설계 설명을 추가하지 않습니다.

## 5. 도구 — Microsoft Learn MCP Server 등록 · 24~31분

### 24~25분 — 선택 기준 표에서 필요한 행동과 출처만 설명

**띄울 위치:** Step3. Tools 등록 → **2절의 구성 기준과 선택 이유**를 정리한 표. ‘필요한 행동’과 ‘신뢰할 출처’ 두 행을 포인터로 짚습니다. 나머지 행은 읽지 않습니다.

> Tool은 에이전트가 정보를 찾거나 작업할 때 사용하는 기능입니다. Project Delivery 에이전트는 Microsoft 기술을 제안하므로 공식 문서를 찾아볼 기능이 필요합니다. 그래서 Learn 도구를 연결합니다. 다른 업무에서도 먼저 ‘어떤 행동이 필요한가’를 정하고 도구를 선택하면 됩니다.

### 25~31분 — 연결·호출 확인 실습

**실습 화면:** Copilot Studio의 도구 추가·연결 화면. 교안 **3. Microsoft Learn MCP Server 등록**의 캡처를 참고해 함께 조작합니다. 연결 후에는 **4. 도구 호출 확인**의 요청 문장을 보여주고, 실제 Preview 화면으로 전환해 실행합니다.

> 도구 추가에서 Microsoft Learn Docs MCP Server를 찾아 주세요. 연결 이름은 본인 이니셜로 구분하고, Project Delivery 에이전트에 추가한 뒤 저장합니다.

**함께 조작:** 도구 추가 → 서버 검색·선택 → 연결 생성 → Project Delivery 에이전트에 추가·저장. 사용하지 않는 Work IQ가 있으면 교안에 따라 제거합니다.

**연결 화면에서 필요한 만큼만 안내**

> Project Delivery 에이전트에 연결할 Learn 도구는 별도 로그인 없이 연결합니다. 연결 이름을 입력하고 만들기를 선택해 주세요.

**연결 후 짧게 실행**

```text
Microsoft Learn MCP를 사용해 Copilot Studio의 GHCP 하네스에 대해 간단하게 설명해줘.
```

> 답변뿐 아니라 실행 기록에 실제 도구 호출과 결과가 있는지 보겠습니다.

**진행:** 호출이 늦으면 준비한 실행 기록에서 확인하고 다음 단계로 이동합니다. MCP 규약 설명은 추가하지 않습니다.

## 6. 지식 연결 · 31~38분

### 31~32분 — 구성 흐름도로 설명

**띄울 위치:** Step4. Knowledge 구성 → **2절의 구성 기준과 선택 이유**를 정리한 표 아래에 있는 ‘예상 질문 → 필요 정보 → 원본 자료 → 용도와 범위 지정 → 검색 검증’ 흐름도. 자료 선택 이유를 말하며 그림을 왼쪽부터 짚습니다.

**연결 구성 설명:** 공통·업무별로 나눈 이유를 말할 때는 바로 아래 **3. 공통·업무별 지식 연결**의 SharePoint 폴더 구성 예를 보여줍니다.

> Knowledge는 에이전트가 참고할 업무 자료입니다. 그림처럼 ‘무엇을 알아야 하는가’부터 정합니다. Project Delivery 에이전트는 적합한 인력을 추천해야 하므로 기술과 경험이 있는 인력표를 연결하고, 문서 구성에는 기존 제안서와 WBS를 참고합니다.
>
> 인력 자료는 여러 작업이 함께 쓰고, 제안서·WBS 사례는 용도별로 나눴습니다. 연결한 뒤에는 자료가 목록에 있는지만 보지 않고, 실제 내용이 검색되는지 확인합니다.

### 32~38분 — 세 지식 연결·조회 확인 실습

**실습 화면:** 교안 **3. 공통·업무별 지식 연결**의 ‘지식 이름 예 / 설명에 입력할 내용’ 표와 실제 Copilot Studio의 지식 추가 화면을 번갈아 보여줍니다. 폴더 URL은 이어지는 등록 절차의 코드 박스 위치에서 안내합니다. 등록 후에는 실제 지식 목록의 세 항목을 띄웁니다.

> SharePoint에서 준비된 폴더 세 개를 연결하겠습니다. 교안의 주소를 사용하고, 이름과 설명에는 인력 추천용인지 문서 참고용인지 구분해 주세요.

**함께 조작**

1. 지식 추가에서 SharePoint 선택.
2. 공통 인력 폴더를 선택하고 이름·설명 입력 후 추가.
3. 제안 참고·WBS 참고 폴더도 같은 방식으로 연결.
4. 목록에 세 항목이 표시되는지 확인.

**이름·설명 입력 시 한 문장**

> 기존 문서는 내용 참고용입니다. 실제 문서 양식은 Skill에 넣은 템플릿을 사용합니다.

**연결이 끝나면 조회**

```text
공통 인력 지식에서 Power Platform에 적합한 후보를 찾아 이름·기술·경험과 출처를 보여줘. 가용성을 모르면 확인 중으로 표시해.
```

> 이름뿐 아니라 추천할 근거가 함께 나오는지 보겠습니다. 자료에 없는 가용성은 확인 중으로 남겨야 합니다.

**진행:** 조회가 지연되면 테스트의 인력 추천 결과에서 이어 확인합니다. 연결 범위나 권한 문제는 개별 지원합니다.

## 7. 테스트 · 38~58분

### 38~39분 — 기대 결과 표로 확인할 세 가지 안내

**띄울 위치:** Step5. 테스트 및 Activity Trace → **2. 정상 흐름과 예외 상황을 함께 테스트하기 → 기본 흐름 확인**의 ‘순서 / 요청 예시 / 기대 결과’ 표. 분석·제안서·상세 WBS의 기대 결과를 한 행씩 짚습니다.

> 이제 직접 요청해 보겠습니다. 세 가지만 보겠습니다. 요청한 일까지만 했는지, 자료에 근거해 답했는지, 파일을 열었을 때 실제로 쓸 수 있는지입니다. 제안서와 WBS에서는 앞에서 정한 인력과 일정도 이어졌는지 확인합니다.
>
> 결과가 다르면 실행 기록을 보고 어디서 달라졌는지 찾겠습니다.

### 39~58분 — 실행·결과 확인·질의응답

| 시간 | 함께 할 일 | 확인할 한 가지 |
|---|---|---|
| 39~42분 | 새 대화에 RFP 첨부 후 분석 요청 | 인력 후보 한 명의 이름과 추천 근거 |
| 42~54분 | 같은 대화에서 제안서 요청 | PowerPoint의 인력·수행계획 페이지 |
| 54~56분 | 상세 WBS 요청, 지연 시 강사 파일 시연 | Excel의 작업·담당자·일정 |
| 56~58분 | 실행 기록 확인 | 결과가 달라진 지점과 고칠 곳 |

**진행 기준:** 표의 시간은 생성 완료 예상 시간이 아닙니다. 선행 결과가 완료된 대화에서만 다음 요청을 실행합니다. 늦어지면 학습자의 실행을 중복 시작하지 않고 같은 RFP의 준비된 강사 대화·파일로 이어 봅니다.

#### RFP 분석

**띄울 위치:** 실제 Copilot Studio의 **Preview 새 대화**. RFP 첨부와 요청 입력을 직접 보여줍니다. 완료 후 응답의 인력 추천 부분과 원본 인력표에서 후보 한 명이 있는 행을 보여줍니다.

> 새 대화에 RFP-01을 첨부하고 다음 요청을 입력해 주세요.

```text
첨부한 RFP를 분석해줘. 지금은 분석만 해줘.
```

**함께 확인:** 인력 후보 한 명을 골라 원본 인력표의 기술·경험과 대조합니다.

> 자료에 있는 후보인지, 추천 이유가 맞는지 보겠습니다. 분석만 요청했으니 문서 작성까지 이어지지 않는지도 확인해 주세요.

#### 제안서 생성

**띄울 위치:** 분석을 완료한 **같은 Preview 대화**의 입력창. 생성 후에는 PPTX를 열어 **인력 또는 수행계획 슬라이드 한 장**을 보여줍니다. 생성 중이라면 사전 준비한 같은 RFP의 PPTX를 엽니다.

> 분석이 끝난 같은 대화에서 요청해 주세요.

```text
이 분석을 바탕으로 제안서를 만들어줘.
```

> 제안서에 필요한 중간 작업 계획도 연결하는지 보겠습니다. 이 계획은 별도 Excel 파일이 아니라 제안서에 쓸 중간 데이터입니다.

**함께 확인:** PPTX를 열고 인력·수행계획 페이지 한 곳을 분석 결과와 대조합니다. 템플릿의 기존 고객명이나 샘플 내용이 남았는지도 봅니다.

#### 상세 WBS 생성

**띄울 위치:** 제안서 결과가 확보된 **같은 Preview 대화**. 생성 후 XLSX에서 **작업·담당자·일정이 함께 보이는 영역**으로 이동합니다. 지연되면 사전 준비한 같은 RFP의 XLSX를 보여줍니다.

> 제안서가 완성된 대화에서 요청해 주세요.

```text
제안서 내용을 반영해서 상세 WBS를 Excel 파일로 만들어줘.
```

**함께 확인:** XLSX의 작업 한 줄을 골라 담당자·일정을 제안서와 대조합니다. 가용성 미확인이 배정 확정으로 바뀌지 않았는지 확인합니다.

**지연 시 공통 발화**

> 아직 생성 중이므로 같은 RFP로 미리 만든 결과에서 확인 방법을 보여드리겠습니다. 본인 파일도 완료되면 같은 기준으로 확인해 주세요.

#### 실행 기록 — Activity Trace

**띄울 위치:** 실제 Preview에서 방금 요청한 작업의 **Activity Trace**를 엽니다. 과거 사례는 **History**에서 준비한 대화를 선택합니다. Skill 선택이나 지식·도구 호출 **한 항목의 입력·결과**만 펼칩니다. 화면 위치를 안내할 때는 교안 **4. Activity Trace로 문제의 시작점 찾기**의 캡처를 참고합니다.

> 실행 기록은 Project Delivery 에이전트가 어떤 기능을 사용하고 어떤 결과를 받았는지 보는 곳입니다. 결과가 잘못됐을 때 고칠 위치를 찾는 데 사용합니다.

**진행:** 대표 요청 하나에서 Skill 선택 또는 자료 조회·도구 호출 하나를 실제로 보여줍니다. 모든 기록을 펼치지 않습니다. Preview의 표시 설정은 실행 기록이 보이는 상태로 맞춥니다.

> 예를 들어 추천 인력이 빠졌다면, 자료 조회부터 안 됐는지, 조회한 이름이 문서에서 빠졌는지 확인합니다. 앞의 문제면 자료 연결을, 뒤의 문제면 문서 작성 방법을 점검합니다. 고친 뒤에는 같은 요청으로 다시 확인합니다.

**대기 중 질의응답:** 질문을 먼저 받습니다. 질문이 없으면 RFP 요구사항 한 항목과 생성 결과를 대조합니다. 긴 개념 설명이나 새 예외 테스트를 시작하지 않습니다.

## 8. 마무리 · 58~60분

**띄울 위치:** 정리 및 마무리 → **1. 이번 실습에서 구성한 것**의 에이전트 구성 관계도. 58~59분 핵심 정리는 이 그림에서 진행합니다.

**완료 확인 시:** **3. 실습 완료 확인**의 체크리스트로 이동합니다. 종료 멘트 순서는 기존 스크립트를 유지합니다.

### 58~59분 — 실습 내용과 핵심 원칙

> 오늘 구성한 내용을 관계도에서 되짚겠습니다. Project Delivery 에이전트 생성 후 지침으로 목표·범위·공통 원칙을 정하고, Skill로 작업별 방법과 완료 기준을 나눴습니다. Tool은 필요한 행동과 출처를 기준으로, Knowledge는 답해야 할 질문과 근거 자료를 기준으로 연결했습니다.
>
> 기억할 원칙은 각 구성의 책임을 분명히 하고, 실제 동작으로 검증하는 것입니다. 지침에 모든 방법을 몰아넣거나 도구·자료를 많이 연결하는 것만으로 품질이 좋아지지는 않습니다. 테스트에서는 기대 결과와 실제 근거·파일을 대조하고, 실행 기록으로 원인을 찾아 해당 구성을 고칩니다. 수정 후에는 같은 입력과 영향을 받는 후속 결과를 다시 확인합니다.

### 59~60분 — 완료 확인과 종료

>  이상으로 오늘 Hands-On Lab을 마치겠습니다. 자리해주셔서 감사합니다.  
체크리스트에서 직접 완료한 항목을 확인해 주세요. 시연으로 확인한 부분과 아직 실행 중이거나 마치지 못한 부분은 추가 실습으로 남겨 두겠습니다.
>
> 교육 후에는 자신의 파일을 열어 오늘 기준으로 점검하고, 다른 RFP나 본인의 업무에도 적용해 보세요. 목표와 범위, 나눌 작업, 필요한 기능·자료, 완료 기준부터 정하면 됩니다. 수고하셨습니다.

## 강사용 빠른 전환표

| 상황 | 대응 |
|---|---|
| 생성·등록·연결이 지연됨 | 학습자의 현재 위치를 기록하고 Project Delivery 에이전트 완성본에서 후속 과정 시연 |
| 분석·파일 생성이 다음 구간까지 끝나지 않음 | 준비한 동일 RFP 대화·파일로 확인 방법 시연 |
| 질문이 길어짐 | 지금 할 동작을 먼저 안내하고 세부 답변은 생성 대기나 종료 후로 이동 |
| 시간이 남음 | 등록 상태 재확인, 개별 지원, 다음 실습 조기 시작 |

준비한 결과를 보여줄 때는 사전 실행 결과임을 밝힙니다. 실제로 확인하지 못한 작업을 완료했다고 설명하지 않습니다.
