# GHCP Harness Hands-on Lab — 60분 강의용 스크립트

교안의 핵심 표·그림을 짚은 뒤 바로 실습합니다. 상세 설계는 교안의 접힌 참고 영역에 남겨 둡니다. 인용문은 발화, ‘띄울 위치’와 ‘진행’은 강사 화면 안내입니다.

## 강의 전 준비

- Contoso(default) 환경의 로그인·생성 권한과 실습 파일 다운로드를 확인합니다.
- SharePoint의 인력·제안·WBS 자료는 미리 준비하고 학습자 접근 권한을 확인합니다.
- 강사용 Project Delivery 에이전트, 같은 RFP의 분석 대화·PPTX·XLSX·실행 기록을 준비합니다.
- 설명은 표 전체를 읽지 않고 핵심 하나와 예 하나만 말합니다. 한 동작을 보여주고 학습자가 따라 할 시간을 줍니다.
- 생성 대기에는 질문을 받거나 학습자 결과의 한 항목만 확인합니다. 긴 설계 설명을 추가하지 않습니다.
- 38분에는 테스트, 58분에는 마무리로 이동합니다. 지연되면 사전 실행 결과임을 밝히고 준비한 대화·파일로 시연합니다.

60분 중 개념 설명은 짧게 진행하고, 나머지는 구성 실습·테스트·시연·질의응답에 사용합니다. 제안서·WBS 생성 시간은 일정하지 않으므로 두 파일의 완성을 기다리며 교육을 멈추지 않습니다.

## 1. 홈 · 00~02분

**띄울 위치:** 홈 → **2. 완성할 에이전트와 업무 흐름**의 업무 흐름도. 목적을 말할 때 바로 위의 ‘프로젝트 산출물 작성, 더 쉽고 빠르게’ 이미지를 잠깐 보여줍니다.

> 안녕하세요. 앞서 소개드린 에이전트 5종 중 Project Delivery 에이전트를 개발한 (회사명) (팀명)팀 (이름) 매니저입니다. 오늘은 고객의 사업 요구 문서인 RFP를 읽고, 제안서와 작업 일정표인 WBS를 만드는 Project Delivery 에이전트를 구성하겠습니다. 견적서는 오늘 범위에서 제외합니다.

>
> Copilot Studio의 Contoso(default) 환경과 실습 파일을 준비해 주세요.

## 2. GHCP Harness 개요 · 02~05분

**띄울 위치:** GHCP 개요 → **1. GHCP Harness로 할 수 있는 일**의 구성 그림. 선택 이유를 말할 때는 바로 아래 **2. Project Delivery 에이전트에서 선택한 이유**의 두 열 표를 보여줍니다.

> 하네스는 AI의 판단을 실제 작업으로 연결하는 환경입니다. 그림의 지침은 전체 규칙, Skill은 작업 방법, Tool은 실행 기능, Knowledge는 참고 자료입니다. 이 요소를 활용해 여러 작업을 이어 하고 PowerPoint·Excel 파일도 만듭니다.
>
> 아래 표를 보면 선택 이유가 세 가지입니다. 분석 결과를 다음 작업에 이어 쓰고, 여러 Skill과 도구·자료를 함께 활용하고, 실제 문서 파일까지 작성해야 했습니다. 직접 구축했을 때 파일 품질도 만족스러워 GHCP를 선택했습니다. 환경에 따라 Microsoft Copilot 하네스로 표시될 수도 있습니다.
>
> 이제 직접 만들어 보겠습니다. 실습 자료는 가상 문서이고, 지식 자료는 SharePoint에 준비되어 있습니다.

**진행:** Agentic Loop와 Standard 비교표는 설명하지 않습니다. 남는 시간은 환경·자료 준비를 지원하거나 다음 실습을 시작합니다.

## 3. 에이전트 생성·지침 · 05~12분

### 05~06분 — 지침의 기본 구성

**띄울 위치:** Step1 → **3. 에이전트 이름 및 지침 입력 → 지침은 어떻게 구성할까?**의 ‘구성 항목 / 정리하면 좋은 내용’ 표.

> 지침을 표처럼 역할·절차·가드레일 등으로 나누면 빠진 기준을 확인하고 원하는 행동을 더 명확하게 적는 데 도움이 됩니다. 필수 목차는 아니며 업무에 맞게 조정할 수 있습니다. 가드레일은 하지 말아야 할 행동과 지켜야 할 제한입니다. Project Delivery 에이전트는 RFP 분석과 문서 작성을 맡기고, 확인되지 않은 사실을 만들지 않도록 했습니다. 아래 지침은 이 기준을 적용한 예입니다.

### 06~12분 — 함께 생성·입력·저장

**띄울 위치:** 실제 Copilot Studio의 에이전트 카드와 편집 화면. 위치를 놓치면 교안 **2. GitHub Copilot 표시가 있는 에이전트 카드 선택**의 캡처로 안내합니다. 지침을 복사할 때는 **준비된 지침 입력·저장 → 에이전트 지침**을 펼칩니다.

> 카드를 선택해 Project Delivery 에이전트를 만들겠습니다. 이름은 ProjectDelivery_HandsOn_본인이니셜 형식으로 입력합니다. 준비된 지침 전체를 안내 영역에 붙여 넣고 저장해 주세요.

**함께 조작:** 생성 → 이름 입력 → 안내 내용 교체 → 저장. 지침 전문을 읽지 않습니다.

> 이름과 지침이 저장됐는지 확인해 주세요. 다음은 업무별 작업 방법을 등록하겠습니다.

## 4. Skill 등록 · 12~24분

### 12~14분 — 세 Skill의 역할

**띄울 위치:** Step2 → **2. 등록할 세 Skill**의 ‘Skill / 맡은 일 / 만드는 결과’ 표. 지침과의 차이는 이 표를 보며 짧게 말합니다.

> 지침이 전체 규칙이라면 Skill은 업무별 작업 방법입니다. 목적·입력·절차·출력 등을 나눠 정리하면 무엇을 받아 어떻게 처리하고 무엇을 만들지 더 명확해집니다. 필요한 항목만 업무에 맞게 활용하면 됩니다. 표처럼 Project Delivery 에이전트는 분석·제안서·WBS를 나눠 맡겼습니다.
>
> Project Delivery 에이전트는 여러 문서의 내용을 맞춰야 하므로 분석 결과를 다음 작업에 넘기도록 구성했습니다. 업무 특성에 맞춰 추가한 규칙입니다. WBS Skill은 중간 계획과 상세 Excel 작성에 함께 사용합니다. 중간 계획은 별도 Excel 파일이 아닙니다.
>
> 제안서와 WBS는 템플릿 원본을 복사해 내용을 바꾸도록 했습니다. 표준 양식을 그대로 사용하기 위한 구성입니다.

**진행:** 긴 Skill 원문과 4절 참고 영역은 펼치지 않습니다.

### 14~24분 — 세 Skill 등록

**띄울 위치:** Step2 → **3. Skill 등록**의 업로드 형식 표를 보여준 뒤 실제 Skill 업로드 화면으로 이동합니다. **3.1 분석 Skill 등록**, **3.2 제안서/WBS Skill 등록** 캡처를 따라갑니다.

> 분석은 압축을 풀어 SKILL.md를 등록합니다. 제안서와 WBS는 템플릿도 함께 필요하므로 ZIP 그대로 등록해 주세요. 하나씩 보여드리면 같은 순서로 따라 해 주세요.

1. 분석 패키지의 SKILL.md 업로드 후 목록 확인.
2. 제안서 ZIP 업로드 후 목록 확인.
3. WBS ZIP 업로드 후 목록 확인.

> 세 Skill이 목록에 보이는지 확인해 주세요. ZIP은 등록용이고, 업무 결과물은 PowerPoint와 Excel입니다.

**진행:** 오류가 나면 선택 파일·업로드 상태부터 확인합니다. 먼저 끝난 학습자는 이름·설명을 확인하고, 아직 진행 중인 학습자를 지원합니다.

## 5. Tool 연결 · 24~31분

### 24~25분 — 필요한 기능 한 가지

**띄울 위치:** Step3 → **1. Tool은 실제 작업에 쓰는 기능**의 그림. 선택 이유를 말할 때 바로 아래 **2. Project Delivery 에이전트에 연결할 도구**의 표를 보여줍니다. 표는 ‘필요한 기능’과 ‘믿을 수 있는 출처’ 두 행만 짚습니다.

> Tool은 실제로 정보를 찾거나 작업하는 기능입니다. 그림처럼 에이전트가 요청하면 도구가 조회 결과를 돌려줍니다. Project Delivery 에이전트는 Microsoft 기술의 지원 조건을 공식 문서에서 확인하려고 Learn 도구를 연결했습니다. 도구를 고를 때는 필요한 기능인지, 믿을 수 있는 정보를 주는지 보고 실제로 실행해 확인하면 됩니다.

### 25~31분 — 연결·호출 확인

**띄울 위치:** 교안 **3. Microsoft Learn MCP Server 등록**의 캡처와 실제 도구 추가 화면. 연결 후 **4. 도구 호출 확인**의 요청 문장을 보여주고 Preview로 이동합니다.

> Microsoft Learn Docs MCP Server를 찾아 주세요. 별도 로그인 없이 연결하고, 연결 이름에 본인 이니셜을 넣어 에이전트에 추가한 뒤 저장합니다.

**함께 조작:** 서버 선택 → 연결 생성 → Project Delivery 에이전트에 추가·저장. Work IQ가 있으면 교안에 따라 제거합니다.

```text
Microsoft Learn MCP를 사용해 Copilot Studio의 GHCP 하네스에 대해 간단하게 설명해줘.
```

> 답변과 실행 기록에 실제 조회 결과가 있는지 보겠습니다.

**진행:** MCP 규약은 설명하지 않습니다. 호출이 늦으면 준비된 기록에서 확인합니다.

## 6. Knowledge 연결 · 31~38분

### 31~32분 — 질문에 맞는 자료

**띄울 위치:** Step4 → **1. Knowledge는 참고할 업무 자료**의 그림. 자료 선택 이유를 말할 때 바로 아래 **2. 어떤 자료가 필요한지 정하기**의 질문·자료 표를 보여줍니다.

> Knowledge는 답변의 근거로 참고할 자료입니다. 그림처럼 인력을 추천하려면 인력표에서 기술과 경험을 확인하고 추천 이유와 출처를 함께 제시합니다. Project Delivery 에이전트는 인력표와 기존 제안서·WBS를 연결했습니다. 자료를 많이 넣기보다 필요한 정보가 실제로 검색되는지 보는 것이 중요합니다.

### 32~38분 — 세 자료 연결·조회 확인

**띄울 위치:** **3. 공통·업무별 지식 연결**의 ‘지식 이름 예 / 설명에 입력할 내용’ 표와 URL 코드 박스. 실제 지식 추가 화면에서 따라 한 뒤 목록의 세 항목을 보여줍니다.

> SharePoint 자료는 준비돼 있습니다. 교안 주소로 인력·제안 참고·WBS 참고 폴더를 연결하겠습니다. 이름과 설명에는 어떤 용도로 쓸 자료인지 적어 주세요.

**함께 조작:** SharePoint 선택 → 폴더 주소 → 이름·설명 → 추가. 세 항목을 반복합니다.

> 기존 문서는 내용 참고용이고, 실제 양식은 Skill의 템플릿을 사용합니다. 연결했으면 실제 내용이 검색되는지 보겠습니다.

```text
공통 인력 지식에서 Power Platform에 적합한 후보를 찾아 이름·기술·경험과 출처를 보여줘. 가용성을 모르면 확인 중으로 표시해.
```

**진행:** 조회가 늦으면 이어지는 분석 결과에서 확인합니다. 폴더 생성·자료 업로드는 하지 않습니다.

## 7. 두 가지 테스트와 파일 시연 · 38~58분

### 38~39분 — 기대하는 결과

**띄울 위치:** Step5 → **1. 먼저 확인할 결과 정하기**의 두 행 표.

> RFP가 있으면 분석하고, 자료가 없으면 필요한 자료를 요청하는지 보겠습니다. 자료가 없는데 내용을 지어내 파일을 만드는 것은 올바른 결과가 아닙니다.

### 39~58분 — 실습·시연·질의응답

| 시간 | 진행 | 화면 |
|---|---|---|
| 39~45분 | RFP 분석 직접 실습 | 교안 2.1 → Preview 새 대화 → 인력 추천 응답 |
| 45~48분 | 자료 없는 상황 직접 실습 | 교안 2.2 → 별도 새 대화 → 자료 요청 응답 |
| 48~56분 | 제안서·WBS 시연 | 준비된 분석 대화 → PPTX 한 장 → XLSX 한 줄 |
| 56~58분 | 실행 기록 하나 확인 | 교안 3절 → 실제 Activity Trace |

#### RFP가 있을 때

> 새 대화에 RFP-01을 첨부하고 요청해 주세요.

```text
첨부한 RFP를 분석해줘. 지금은 분석만 해줘.
```

**띄울 위치:** 실제 Preview의 새 대화. 결과가 나오면 추천 후보 한 명과 원본 인력표의 해당 행을 보여줍니다.

> 자료에 있는 이름인지, 추천 이유가 맞는지 확인해 주세요. 분석만 요청했으므로 문서 작성까지 이어지지 않는지도 봅니다.

#### RFP가 없을 때

> 이번에는 별도의 새 대화를 열고 파일 없이 요청해 주세요. 앞의 분석 대화는 남겨 둡니다.

```text
이전에 분석한 자료로 제안서를 만들어줘.
```

> 새 대화에 없는 자료를 요청하는지 보겠습니다. 필요한 자료를 물어보는 것도 올바른 동작입니다.

#### 제안서·WBS 시연

**띄울 위치:** 교안 **3. 시연으로 최종 파일과 실행 기록 보기**의 표. 이어서 **분석 결과가 있는 강사용 Project Delivery 에이전트의 대화**를 엽니다. 입력 부족 테스트 대화에서 이어 실행하지 않습니다.

> 이제 분석 결과가 있는 대화에서 문서를 만드는 과정을 보겠습니다. 생성에 시간이 걸리므로 같은 RFP로 미리 실행한 대화와 파일을 함께 보여드리겠습니다.

**보여줄 요청:** ‘이 분석을 바탕으로 제안서를 만들어줘.’ → ‘제안서 내용을 반영해서 상세 WBS를 Excel 파일로 만들어줘.’

**보여줄 파일:** PPTX의 인력·수행계획 슬라이드 한 장 → XLSX의 작업·담당자·일정 한 줄.

> 파일이 있다는 것만 보지 않고, 분석한 인력과 작업 내용이 이어졌는지 확인합니다. 고객에게 전달하기 전에는 내용을 검토하고 수정·보완해야 합니다.

#### 실행 기록 하나 확인

**띄울 위치:** 실제 Preview의 Activity Trace. 이전 기록은 History에서 준비한 대화를 선택합니다. 분석 Skill 실행 한 항목만 펼칩니다. 화면 위치 안내는 교안 **3절의 실행 기록 캡처**를 사용합니다.

> 실행 기록은 어떤 작업을 했는지 보여줍니다. 분석 Skill이 실행된 항목 하나를 보겠습니다. 결과가 이상할 때는 이런 기록에서 어디서 달라졌는지 찾고, 고친 뒤 같은 요청으로 다시 확인합니다.

**진행:** 생성 대기에 질문을 받습니다. 분석이 늦으면 준비한 결과로 확인 방법을 보여주고, 학습자에게 같은 요청을 중복 입력시키지 않습니다. 예외 사례나 상세 진단을 추가하지 않습니다.

## 강사용 빠른 전환표

| 상황 | 대응 |
|---|---|
| 생성·등록·연결 지연 | 현재 위치를 기록하고 완성 에이전트로 후속 과정 시연 |
| 분석이 늦게 완료됨 | 동일 RFP의 사전 결과로 확인 방법을 설명하고 다음 사례 진행 |
| 질문이 길어짐 | 지금 할 동작을 먼저 안내하고 자세한 답은 대기 또는 종료 후로 이동 |
| 시간이 남음 | 등록 상태 재확인·개별 지원·분석 결과 대조 |

시연한 파일은 학습자의 직접 생성 결과와 구분합니다. 확인하지 않은 작업을 완료했다고 설명하지 않습니다.
