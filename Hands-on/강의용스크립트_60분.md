# Microsoft Copilot Harness Hands-on Lab 비기너 교안 기준 60분 강의 스크립트

핵심 표·그림을 짚고, 짧게 설명한 뒤 함께 조작합니다. 인용문은 실제 발화이며, ‘화면’과 ‘진행’은 강사용 메모입니다. 부록은 기본 설명에서 제외하고 질문이 있을 때만 참고합니다.

## 강의 전 준비

- Copilot Studio의 Contoso(default) 환경에서 생성·Skill 등록·도구·지식 연결이 가능한지 확인합니다.
- 홈의 실습 자료를 미리 내려받게 하고, 교육용 SharePoint 폴더 접근 권한을 확인합니다.
- 강사용 Project Delivery 에이전트와 같은 RFP로 실행한 분석 대화·PPTX·XLSX·실행 기록을 준비합니다.
- 교안과 Copilot Studio를 별도 탭에 열고, 파일 시연용 PowerPoint·Excel도 준비합니다.
- 설명 중에는 핵심 화면 하나를 유지합니다. 조작은 한 번 보여주고 기다린 뒤 완료 화면을 확인합니다.
- 학습자가 입력하는 동안 추가 개념을 설명하지 않습니다. 질문은 실행 대기에 받습니다.

## 1. 홈 00~02분

**화면:** 홈 상단에서 자기소개 후 **2. 완성할 에이전트와 업무 흐름**의 목적 이미지를 보여줍니다. 에이전트 소개에 약 1분, 업무 흐름에 약 30초, 실습 안내에 약 30초를 사용합니다.

> 안녕하세요. 앞서 소개드린 에이전트 5종 중 Project Delivery 에이전트를 개발한 (회사명) (팀명)팀 (이름) 매니저입니다. Project Delivery 에이전트는 제안서·WBS·견적서 같은 프로젝트 산출물의 초안을 작성합니다. 오늘은 견적서를 제외하고 RFP 분석·제안서·WBS를 구성해 보겠습니다.
>
> 프로젝트 문서를 만들 때는 고객 요구사항을 읽고, 자료를 찾고, 문서마다 내용을 정리하는 작업이 반복됩니다. Project Delivery 에이전트는 이 수작업을 줄이고, 근거 있는 내용으로 초안을 빠르게 만들기 위해 개발했습니다. 실제 구축 경험에서는 약 3일 걸리던 초안 작성을 약 1시간으로 줄였습니다. 초안은 사람이 검토하고 수정·보완해 고객에게 전달합니다.

**다음 화면:** 바로 아래 업무 흐름도. 분석부터 상세 WBS까지 순서대로 짚습니다.

> 그럼 어떤 순서로 문서를 만드는지 보겠습니다. RFP라는 고객의 사업 요구 문서를 분석해 구축 계획을 정리하고, 인력 자료에서 적합한 후보를 추천합니다. 그 내용으로 중간 작업 계획과 제안서를 만들고, 마지막으로 작업·담당자·일정을 담은 상세 WBS를 Excel로 작성합니다. 앞에서 정한 내용이 문서마다 일관되게 이어지도록 구성했습니다.
>
> 이제 Project Delivery 에이전트를 함께 구성하면서, 업무를 맡기고 필요한 기능과 자료를 연결해 에이전트를 만드는 방법을 배워보겠습니다.

**실습 안내 화면:** **1. 학습 목표와 준비사항 → 사용할 자료**. 지침·Skill·RFP 위치만 짚고 실제 환경 이름을 확인합니다.

> 오늘은 준비된 지침과 Skill을 등록하고 도구·자료를 연결한 뒤 두 가지 테스트를 해보겠습니다. 최종 문서 파일은 제 화면으로 함께 확인하겠습니다. Contoso(default) 환경과 내려받은 실습 파일을 준비해 주세요.

**확인:** 로그인·환경·실습 파일. 다운로드가 필요하면 **시작 전 확인**의 링크를 안내합니다. 자료 목록은 읽지 않고 에이전트 소개에 시간을 배분합니다.

## 2. Microsoft Copilot Harness 개요 02~05분

**화면:** **1. Microsoft Copilot Harness로 할 수 있는 일**의 구성 그림. 네 구성 요소와 맨 아래 결과 영역을 짚습니다.

> 하네스는 AI의 판단을 실제 작업으로 연결하는 실행 환경입니다. 그림에서 지침은 전체 규칙, Skill은 업무별 방법, Tool은 실제로 쓸 기능, Knowledge는 참고할 자료입니다. 이 요소를 연결하면 자료를 확인하고 PowerPoint·Excel 파일을 만드는 작업까지 진행할 수 있습니다.

**다음 화면:** **2. Project Delivery 에이전트에서 선택한 이유**의 표.

> Project Delivery 에이전트는 분석부터 문서 작성까지 여러 작업을 연결하고, 도구와 자료도 함께 사용해야 했습니다. 이런 업무에 적합했고, 직접 구축했을 때 파일 작성 품질도 만족스러워 Microsoft Copilot Harness를 선택했습니다.
>
> 일부 캡처에는 이전 명칭인 GitHub Copilot이 보일 수 있습니다. 이제 직접 구성해 보겠습니다.

**진행:** 부록의 Standard 비교와 Agentic Loop는 설명하지 않습니다. 시간이 남으면 환경·파일 준비를 돕거나 다음 실습을 시작합니다.

## 3. 에이전트 생성과 지침 05~12분

### 05~06분 에이전트 생성

**화면:** 교안 **2. Microsoft Copilot Harness 에이전트 카드 선택**의 캡처를 보여주고, 실제 Copilot Studio 홈으로 이동합니다.

> 표시된 에이전트 카드를 선택해 주세요. 편집 화면이 열리면 Project Delivery 에이전트의 이름을 입력하겠습니다.

**따라 하기:** 카드 선택 → 편집 화면 열림 확인. 이어서 교안 **3. 에이전트 이름 및 지침 입력**으로 이동합니다.

### 06~07분 지침 구성표 설명

**화면:** **지침은 어떻게 구성할까?**의 ‘구성 항목 / 정리하면 좋은 내용’ 표.

> 지침은 전체 업무에서 지킬 기준입니다. 역할·범위·절차·응답 형식·가드레일로 나눠 보면 빠진 내용을 확인하기 쉽습니다. 가드레일은 하지 말아야 할 행동이나 제한입니다. 필수 목차는 아니며 업무에 맞게 조정하면 됩니다.
>
> Project Delivery 에이전트는 분석과 문서 작성을 맡기고, 확인되지 않은 사실은 만들지 않도록 정했습니다. 준비된 지침에서 이 부분을 짚어보겠습니다.

**진행:** 아래 지침을 펼쳐 ‘역할과 범위’와 ‘공통 원칙’의 대표 문장만 보여줍니다. 단계 간 결과 유지는 Project Delivery 에이전트의 적용 사례이며, 일반적인 지침의 필수 항목으로 설명하지 않습니다.

### 07~12분 이름·지침 입력과 저장

**화면:** **에이전트 이름 입력**, **준비된 지침 입력·저장**과 실제 편집 화면.

> 이름은 ProjectDelivery_HandsOn_본인이니셜로 입력합니다. 본인이니셜 부분을 바꿔 주세요. 펼침 영역의 지침 전체를 복사해 안내 영역의 기본 내용을 교체하고 저장합니다.

**함께 조작:** 이름 입력 → 지침 복사·붙여넣기 → 저장.

> 이름과 지침이 저장됐는지 확인해 주세요. 다음은 업무별 작업 방법을 등록하겠습니다.

## 4. Skill 등록 12~24분

### 12~14분 역할과 등록 파일 설명

**화면:** **1. Skill은 업무별 작업 방법**의 지침·Skill 비교표 → **2. 등록할 세 Skill**의 역할 표.

> 지침이 전체 규칙이라면 Skill은 특정 업무의 작업 방법입니다. 예를 들어 지침에는 어떤 일을 맡길지 적고, Skill에는 제안서 파일을 어떻게 만들지 적습니다.
>
> 표처럼 Project Delivery 에이전트는 분석·제안서·WBS를 나눠 맡겼습니다. 목적과 입력, 절차와 결과를 구분해 적으면 작업 방법을 더 명확하게 전달하는 데 도움이 됩니다.
>
> Project Delivery 에이전트에서는 문서 간 내용을 맞추기 위해 분석 결과를 이어 쓰도록 했습니다. 같은 WBS Skill이 중간 계획과 상세 Excel을 만듭니다. 중간 계획은 별도 Excel 파일이 아닙니다.

**다음 화면:** **3. Skill 등록**의 업로드 형식 표.

> 분석은 SKILL.md 하나를, 제안서와 WBS는 템플릿이 들어 있는 ZIP을 등록합니다. 템플릿은 원본을 복사해 내용을 바꾸도록 했습니다. 표준 양식을 그대로 적용하기 위한 구성입니다.

**진행:** 4절 부록은 펼치지 않습니다. 구조와 템플릿의 상세 비교는 질문이 있을 때만 참고합니다.

### 14~24분 세 Skill 등록

**화면:** 실제 **빌드 → 기술(Skills) 옆 + → 기술 업로드**. 교안 **3.1 분석 Skill 등록**, **3.2 제안서/WBS Skill 등록**의 캡처를 순서대로 보여줍니다.

> 먼저 분석 패키지의 압축을 풀고 SKILL.md를 선택합니다. 등록이 끝나면 목록에서 이름과 설명을 확인해 주세요.

**기다린 뒤 확인:** 분석 Skill 1개 표시.

> 같은 메뉴에서 제안서 ZIP을 올리겠습니다. 템플릿도 전달해야 하므로 압축을 풀지 않습니다. 제안서 등록이 끝나면 WBS ZIP도 같은 방법으로 올려 주세요.

**기다린 뒤 확인:** 분석·제안서 생성·WBS 생성 세 개 표시.

> 세 Skill이 보이면 등록이 끝났습니다. ZIP은 등록용이고, 실제 업무 결과는 PowerPoint와 Excel입니다.

## 5. Tools 등록 24~31분

### 24~25분 역할과 선택 이유

**화면:** **1. Tool은 실제 작업에 쓰는 기능**의 그림 → **2. Project Delivery 에이전트에 연결할 도구**의 표. 표에서는 기능과 출처 두 행만 짚습니다.

> Tool은 실제로 검색하거나 작업하는 기능입니다. 그림처럼 에이전트가 요청하면 도구가 실행 결과를 돌려줍니다. Project Delivery 에이전트는 Microsoft 기술의 지원 조건을 공식 문서에서 확인하려고 Learn 도구를 연결합니다. 도구를 고를 때는 필요한 기능인지, 믿을 수 있는 정보를 주는지 살펴보면 됩니다.

### 25~31분 연결과 조회 확인

**화면:** **3. Microsoft Learn MCP Server 등록**의 캡처와 실제 도구 추가 화면.

> Microsoft Learn Docs MCP Server를 찾아 선택해 주세요. 연결 이름에 본인 이니셜을 넣고, Project Delivery 에이전트에 추가한 뒤 저장합니다.

**함께 조작:** 서버 선택 → 연결 생성 → 추가·저장. 별도 로그인 없이 연결하는 화면을 보여주고, Work IQ가 있으면 교안에 따라 제거합니다.

**다음 화면:** **4. 도구 호출 확인**의 요청 문장 → 실제 Preview.

```text
Microsoft Learn MCP를 사용해 Copilot Studio의 Microsoft Copilot Harness에 대해 간단하게 설명해줘.
```

> 연결 목록에 있는 것에서 끝내지 않고 실제로 조회되는지 보겠습니다. 답변과 실행 기록에 문서 내용과 출처가 나오는지 확인해 주세요.

**진행:** 조회가 늦으면 준비한 기록을 보여주고 이동합니다. MCP 규약과 부록은 설명하지 않습니다.

## 6. Knowledge 구성 31~38분

### 31~32분 역할과 자료 용도

**화면:** **1. Knowledge는 참고할 업무 자료**의 그림 → **2. 어떤 자료가 필요한지 정하기**의 표.

> Knowledge는 답변의 근거로 참고할 자료입니다. 그림처럼 인력을 추천하려면 이름뿐 아니라 기술과 경험을 확인해야 합니다. Project Delivery 에이전트는 인력표와 기존 제안서·WBS를 연결합니다. 자료를 많이 넣기보다 필요한 정보가 실제로 검색되는지 보는 것이 중요합니다.

### 32~38분 세 지식 연결

**화면:** **3. 공통·업무별 지식 연결**의 ‘지식 이름 예 / 설명에 입력할 내용’ 표. 이어서 폴더 주소 코드 박스와 실제 지식 추가 화면을 보여줍니다.

> 폴더와 자료는 SharePoint에 준비되어 있습니다. 인력 자료는 공통으로 사용하고, 제안서·WBS 사례는 참고할 용도에 맞춰 나눠 놓았습니다. Project Delivery 에이전트의 자료 구성 사례입니다.
>
> 지식 추가에서 SharePoint를 선택하고 교안의 폴더 주소를 넣어 주세요. 이름과 설명을 입력해 추가합니다. 같은 방법으로 세 항목을 연결하겠습니다.

**함께 조작:** 공통 인력 1개 등록 → 목록 확인 → 제안 참고·WBS 참고 등록 → 총 3개 확인.

> 기존 문서는 내용 참고용입니다. 실제 문서 양식은 Skill에 넣은 템플릿을 사용합니다. 이제 필요한 내용이 검색되는지 확인하겠습니다.

**화면:** 교안의 지식 조회 확인 예시를 보여주고 Preview로 이동합니다.

```text
공통 인력 지식에서 Power Platform·API 연계·문서 추출에 적합한 후보를 찾아, 이름·원문 Level·업무 근거·출처를 보여줘. 가용성을 확인하지 못하면 확인 중으로 표시해.
```

> 이름과 추천 이유, 출처를 함께 보겠습니다. 자료에 가용성이 없으면 확인 중으로 남겨야 합니다.

**진행:** 조회가 늦으면 분석 테스트에서 이어 확인합니다. 폴더 생성이나 자료 업로드 실습은 하지 않습니다.

## 7. 테스트와 결과 시연 38~58분

### 38~39분 기대 결과 설명

**화면:** **1. 먼저 확인할 결과 정하기**의 두 행 표.

> 두 가지를 해보겠습니다. RFP가 있으면 분석하고, 자료가 없으면 필요한 자료를 요청하는지 확인합니다. 자료가 없을 때 물어보는 것도 올바른 동작입니다. 내용을 지어내 문서를 만드는 것이 성공은 아닙니다.

### 39~45분 RFP가 있을 때 직접 테스트

**화면:** **2.1 RFP가 있을 때**의 첨부·입력 캡처 → 실제 Preview 새 대화.

> 새 대화에 RFP-01을 첨부하고 아래 요청을 입력해 주세요.

```text
첨부한 RFP를 분석해줘. 지금은 분석만 해줘.
```

**파일:** 교안과 같은 `RFP-01_물류운영포털.md`를 기본으로 사용합니다. Word 버전을 준비했다면 같은 내용의 `.docx`로 바꿔 첨부할 수도 있습니다.

**완료 후 화면:** 인력 후보 한 명의 이름·추천 이유와 원본 인력표의 해당 행.

> 자료에 있는 인물인지, 추천 이유가 자료와 맞는지 확인해 주세요. 분석만 요청했으므로 제안서나 WBS 작성까지 이어지지 않는지도 보겠습니다.

**대기:** 질문을 받거나 RFP 요구사항 한 항목을 결과와 비교합니다. 같은 요청을 중복 입력시키지 않습니다.

### 45~48분 자료가 없을 때 직접 테스트

**화면:** **2.2 RFP가 없을 때** → 실제 Preview의 별도 새 대화.

> 앞의 분석 대화는 남겨 두고, 별도 새 대화를 열어 주세요. 파일 없이 다음 요청을 입력합니다.

```text
이전에 분석한 자료로 제안서를 만들어줘.
```

> 새 대화에 없는 자료를 요청하는지 확인해 주세요. RFP나 분석 결과를 물어보면 기대한 동작입니다.

**확인:** 두 응답을 각각 기대 결과 표와 대조합니다. 다르면 요청과 실제 응답을 기록해 둡니다.

### 48~56분 제안서와 WBS 시연

**화면:** **3. 시연으로 최종 파일과 실행 기록 보기**의 표 → 분석이 완료된 강사용 Project Delivery 에이전트 대화.

> 이제 최종 문서가 어떻게 만들어지는지 보겠습니다. 생성 시간이 길어질 수 있어 같은 RFP로 미리 실행한 대화와 파일을 보여드리겠습니다.

**보여줄 순서**

1. 분석이 완료된 대화에서 `이 분석을 바탕으로 제안서를 만들어줘.` 요청과 결과 확인.
2. PPTX를 열어 인력·수행계획 슬라이드 한 장 확인.
3. 같은 대화의 `제안서 내용을 반영해서 상세 WBS를 Excel 파일로 만들어줘.` 요청과 결과 확인.
4. XLSX를 열어 작업·담당자·일정 한 줄 확인.

> 중간 작업 계획은 제안서에 쓸 데이터이고, 상세 단계에서 실제 Excel을 만듭니다. 분석한 인력과 내용이 문서에서도 이어지는지 보겠습니다. 파일을 만든 뒤에도 고객 전달 전에는 사람이 검토·수정·보완해야 합니다.

**진행:** 입력 부족 테스트 대화에서 후속 문서 작성을 이어 하지 않습니다. 학습자가 직접 만든 파일과 강사 시연 파일을 구분합니다.

### 56~58분 실행 기록 한 항목 확인

**화면:** 교안 **3절의 실행 기록 캡처** → 실제 Preview의 Activity Trace. 과거 대화는 History에서 선택합니다.

> 실행 기록은 Project Delivery 에이전트가 어떤 작업을 했는지 보여줍니다. 분석 Skill이 실행된 항목 하나만 보겠습니다. 결과가 이상할 때는 기록을 보고 어디서 달라졌는지 찾는 데 사용할 수 있습니다.

**진행:** 한 항목의 입력·결과만 펼칩니다. 기록이 보이는 표시 상태로 맞추고, ON/OFF 명칭을 외우게 하지 않습니다. 부록의 상세 진단·재검증은 기본 강의에서 다루지 않습니다.

## 8. 정리와 마무리 58~60분

### 58~59분 구성 관계도로 정리

**화면:** **1. 이번 실습에서 구성한 것**의 관계도 → **3. 실습 완료 확인**의 체크리스트.

> Project Delivery 에이전트에 전체 규칙과 세 가지 업무 방법을 등록하고, 필요한 기능과 자료를 연결했습니다. 두 요청을 직접 실행하고, 최종 파일과 실행 기록은 시연으로 확인했습니다.
>
> 다른 업무에서도 맡길 일과 필요한 기능·자료를 정한 뒤 작은 요청부터 실행해 보시면 됩니다. 체크리스트에서 직접 완료한 것과 시연으로 본 것을 구분해 주세요.

### 59~60분 — 완료 확인과 종료

>  이상으로 오늘 Hands-On Lab을 마치겠습니다. 자리해주셔서 감사합니다.  
체크리스트에서 직접 완료한 항목을 확인해 주세요. 시연으로 확인한 부분과 아직 실행 중이거나 마치지 못한 부분은 추가 실습으로 남겨 두겠습니다.
>
> 교육 후에는 자신의 파일을 열어 오늘 기준으로 점검하고, 다른 RFP나 본인의 업무에도 적용해 보세요. 목표와 범위, 나눌 작업, 필요한 기능·자료, 완료 기준부터 정하면 됩니다. 수고하셨습니다.

## 진행이 늦어졌을 때

| 상황 | 대응 |
|---|---|
| 생성·등록·연결이 늦음 | 현재 위치를 남기고 강사용 Project Delivery 에이전트에서 후속 과정 시연 |

준비한 결과는 사전 실행 결과임을 밝힙니다. 실제 확인하지 않은 작업을 완료했다고 설명하지 않습니다.
